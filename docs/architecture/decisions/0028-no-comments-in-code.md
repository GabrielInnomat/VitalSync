# 0028. No comments in code

- **Status:** Accepted
- **Date:** 2026-08-03
- **Supersedes:** [ADR-0013](./0013-xml-documentation-conventions.md)
- **Amended:** 2026-08-03 (scope covers every hand-written file, not only C#)

## Context

[ADR-0013](./0013-xml-documentation-conventions.md) required XML documentation on the whole public
surface of `BuildingBlocks/src/*`, with a `<remarks>` block carrying the _why / how / when_ behind
almost every type and method. It was enforced by promoting `CS1591` to a warning in the
`BuildingBlocks` source folders, and `GenerateDocumentationFile` was on solution-wide.

Living with that convention exposed the costs it was meant to avoid:

1. **The documentation drifted from the code.** Comments are not compiled and not tested. Renames,
   signature changes, and behavior changes went in without the surrounding prose following them, so
   the `<remarks>` describing _why_ a member exists slowly became the least trustworthy statement
   about it. A stale comment is worse than no comment, because it is believed.
2. **The ceremony crowded out the code.** `BuildingBlocks/src/*` carried roughly 1900 lines of XML
   documentation. Reading a type meant scrolling past its documentation; reviewing a change meant
   reviewing the prose twice — once for accuracy, once for the ADR-0013 wording table.
3. **Quality was never machine-checkable.** `CS1591` only proves a comment is _present_. The rules
   that actually mattered — "must add insight", "must not restate the summary" — stayed a review
   responsibility, which is exactly the kind of rule that erodes.
4. **Ordinary comments showed the same failure mode.** Inline `//` comments explaining what a block
   does are a signal that the block should have been a named method, and the ones explaining _why_
   belong in an ADR, where they are versioned, reviewed, and discoverable.

The forces that originally justified ADR-0013 have not disappeared — a reader still needs to know
why a building block exists. What changed is where that answer belongs: in the architecture docs and
the ADRs, which are reviewed as documents, rather than scattered across source files where nothing
keeps them honest.

## Decision

**Code contains no comments.** This applies to every hand-written C# source file in the repository
(`BuildingBlocks/**`, `src/**`, `samples/**`, `tests/**`) and covers:

- XML documentation comments (`///`, `<summary>`, `<remarks>`, `<param>`, `<inheritdoc/>`, …),
- ordinary line comments (`//`), including trailing ones,
- block comments (`/* … */`),
- commented-out code.

> **Amendment, 2026-08-03 — every hand-written file, not only C#.** The scope above stopped at
> `*.cs`, which left the same drift free to accumulate one file type over. It now also covers
> MSBuild and solution files (`*.csproj`, `*.props`, `*.targets`, `*.slnx` — no `<!-- … -->`),
> workflows (`*.yml`, `*.yaml` — no `#`), and the fenced **code examples** in `*.md`. The decision
> is unchanged; only the file set is.
>
> Untouched: `.editorconfig` (the enforcement surface itself), accepted ADRs (immutable, so the
> annotated snippet in [ADR-0009](./0009-business-rules-and-domain-validation.md) stays as
> accepted), and the `#` labels in the repository-map tree of the instruction files, which are
> leader lines in a drawing rather than comments. A `//` inside a `text` fence is a comment and
> goes — the fence language decides nothing, the marker does.

### The only exception: generated files

Generated code is exempt, because it is not ours to edit and is overwritten on regeneration. In
practice this is EF Core's scaffolded output under `**/Migrations/**`, which the root `.editorconfig`
marks with `generated_code = true`, and compiler/SDK output under `obj/`. Their `// <auto-generated/>`
markers and any other generated prose stay untouched.

`#pragma` directives, attributes, and `#region`/`#if` are not comments and are unaffected — but a
`#pragma warning disable` must stand on its own, without a trailing comment justifying it.

### Whoever finds a comment removes it

There is no deprecation period and no "clean it up later" backlog. A comment encountered while
working on a file is deleted in that same change, regardless of who wrote it or why the file was
opened. This keeps the rule at zero rather than at "mostly zero", which is the only level at which
the absence of a comment carries information.

### Where the knowledge goes instead

Removing comments does not remove the need to explain. The replacements, in order of preference:

1. **Naming and structure.** A comment explaining _what_ a block does is a missing method name, a
   missing local variable name, or a missing type. Extract it.
2. **Tests.** A comment explaining _how_ a member is meant to be used is an unwritten test. Tests are
   executable, so they cannot go stale silently — the reason `AggregateConventionTests`,
   `HostBuilderWiringTests`, and the container-backed persistence tests exist.
3. **ADRs and `docs/architecture/*`.** A comment explaining _why_ a design is the way it is belongs in
   an ADR, where it is dated, immutable, superseded rather than edited, and findable from the index.
4. **The instruction files.** Conventions that apply repo-wide belong in `.claude/CLAUDE.md` and
   `.github/copilot-instructions.md`, not repeated in every file that follows them.

### Enforcement

Enforcement is deliberately partial, and that is accepted:

- `CS1591` (missing XML comment) is set to `None` in the root `.editorconfig`, and
  `GenerateDocumentationFile` is removed from `Directory.Build.props`, so nothing asks for XML docs
  any more and no XML documentation file is produced.
- No analyzer proves a file is comment-free — that is a review responsibility, the same way comment
  _quality_ was under ADR-0013. The difference is that "is there a `//` in this diff?" is a
  mechanical question with one right answer, while "does this `<remarks>` add insight?" was not.

## Consequences

- Source files are shorter and there is exactly one description of any behavior: the code itself.
  Nothing can contradict it.
- No XML documentation file ships with the `BuildingBlocks` assemblies, so consumers get no IntelliSense
  prose. This is a real loss and is accepted: `BuildingBlocks` is consumed inside this repository, by
  developers who can read its source and its ADRs, not distributed as a third-party package. If it is
  ever published externally, that changes the trade-off and needs a superseding ADR.
- Pressure moves onto naming, decomposition, and tests. Code that needed a comment to be understood
  now needs to be restructured — which is the intended effect, and the main ongoing cost.
- Roughly 2500 lines of comments were deleted from 159 files in the change that adopted this ADR.
  Everything they said that was still true and still worth saying lives in `docs/architecture/`.
- The `.editorconfig` files under `BuildingBlocks/src/*` no longer promote `CS1591`, so
  `BuildingBlocks.Infrastructure` needs no `.editorconfig` of its own at all.
- Reviews get faster and less subjective: there is no wording table to enforce and no argument about
  whether a `<remarks>` earns its place.

## Alternatives considered

- **Keep ADR-0013 as-is:** rejected — the drift and the review cost are what motivated this change,
  and neither is fixable by restating the convention more precisely.
- **Keep XML docs but drop `<remarks>`:** rejected — the summaries are the part that most reliably
  restates the signature (`Gets the unique identifier of the aggregate root.` above
  `public TKey Id`), so this would have removed the useful half and kept the ceremonial half.
- **Allow "why" comments, forbid "what" comments:** rejected — the distinction is not reviewable in
  practice, every comment's author believes theirs explains _why_, and a rule that cannot be applied
  mechanically decays back to "comments allowed". ADRs already own the _why_, with versioning that
  inline prose cannot offer.
- **Enforce comment-freedom with an analyzer or a CI grep:** not adopted for now — a naive text scan
  cannot distinguish generated files, string literals containing `//`, and `#pragma` justifications
  without becoming its own maintenance burden. Revisit if review turns out to miss comments in practice.
- **Keep XML docs only on the `BuildingBlocks` public API surface:** rejected — that is ADR-0013's
  scope, and it is precisely where the drift was observed, because that surface changes with every
  ADR that reshapes the aggregate, repository, or wiring contracts.
