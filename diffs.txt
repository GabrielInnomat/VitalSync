[1] KRITISCH — Outbox ist komplett handgerollt statt Wolverine's nativem Outbox zu nutzen
-------------------------------------------------------------------------------------------------
Doku:
  - docs/architecture/decisions/0023-wolverine-messaging-transport.md:
    "Wolverine ... runs side-by-side with it, sharing a transaction and a native,
    PostgreSQL-backed transactional outbox. This lets the outbox write and the domain
    write commit in the same unit-of-work transaction."
    "Outbox in the unit of work. Integration-event signals are enqueued to Wolverine's
    outbox inside the write transaction ... This is the mechanism ADR-0022 already
    relies on; only the concrete library behind the outbox changes."
  - docs/architecture/decisions/0022-event-driven-read-models.md:
    "the outbox already needed for ADR-0004 is reused" (jetzt: Wolverine-Outbox statt
    MassTransit-Outbox).
  - docs/architecture/building-blocks-infrastructure.md §2 "Unit of work":
    "Wolverine's native Marten/EF Core integration provides the shared transaction +
    outbox enlistment (ADR-0023)."
  - docs/architecture/building-blocks-infrastructure.md §4 "Transactional outbox &
    Publisher": "domain events are written to Wolverine's PostgreSQL-backed outbox
    inside the write transaction".

Code:
  - BuildingBlocks.Infrastructure/Outbox/OutboxMessage.cs, EfCoreOutboxStore.cs,
    MartenOutboxStore.cs, OutboxMessageFactory.cs, OutboxMessageSerializer.cs,
    OutboxRetryPolicy.cs, OutboxSignal.cs, OutboxDrainer.cs, OutboxProcessor.cs,
    OutboxModelBuilderExtensions.cs
    implementieren eine vollständig selbstgebaute Outbox-Tabelle/-Session-Dokument mit
    eigenem Drain-Loop (BackgroundService + Polling + Signal), eigener Serialisierung
    und eigener Exponential-Backoff-Retry-Logik.
  - Wolverine wird ausschließlich in Messaging/WolverineIntegrationEventTransport.cs
    verwendet — dort nur als dünner Publish-Client (`IMessageBus.PublishAsync`), der
    erst NACH dem eigenen OutboxDrainer aufgerufen wird. Es gibt keine Wolverine-
    Transaktions-/Outbox-Enlistment mit EF Core oder Marten.
  - .csproj referenziert nur `WolverineFx.RabbitMQ` — keine `WolverineFx.Marten`
    oder `WolverineFx.EntityFrameworkCore`-Integrationspakete, die für die in der
    Doku beschriebene "native Marten/EF Core integration" nötig wären.

Konsequenz: Die zentrale Begründung von ADR-0023 (Wechsel MassTransit -> Wolverine
WEGEN des nativen, transaktionalen Outbox-Vorteils) wird durch die Implementierung
nicht eingelöst — es wurde stattdessen ein eigenes Outbox-Rad gebaut, das genau die
Komplexität reproduziert, die Wolverine laut ADR bereits mitbringt.

Empfehlung: Entweder (a) die Wolverine/Marten- bzw. Wolverine/EF-Core-Integration
tatsächlich verwenden (Outbox-Klassen im BuildingBlocks.Infrastructure/Outbox/*
Ordner entsprechend ersetzen/entfernen), oder (b) falls die handgerollte Lösung
bewusst gewählt wurde, ADR-0023 und building-blocks-infrastructure.md §2/§4/§6 per
neuem/aktualisiertem ADR anpassen, damit Doku und Code wieder übereinstimmen.

[7] NIEDRIG / ZU VERIFIZIEREN — Möglicher Bug: falsche expectedVersion bei Marten-Append
-------------------------------------------------------------------------------------------------
Doku:
  - docs/architecture/building-blocks-infrastructure.md §3 "Marten event-sourced
    repository": "append uncommitted domain events to the stream with expected-
    version optimistic concurrency asserted against the aggregate's Version."
  - BuildingBlocks.Application/IEventSourcedRepository.cs (XML-Doc): dieselbe
    Aussage.

Code:
  - BuildingBlocks.Infrastructure/Persistence/MartenEventSourcedRepository.cs,
    SaveAsync:
    ```
    session.Events.Append(streamKey, eventSourced.Version, uncommittedEvents);
    var basePosition = eventSourced.Version - uncommittedEvents.Count;
    ```
  - `Version` wird in EventSourcedAggregateRoot (BuildingBlocks.Domain) bei JEDEM
    `RaiseEvent`-Aufruf sofort inkrementiert (siehe EventSourcedAggregateRoot.cs,
    Zeile 84: `_version++`). D.h. `eventSourced.Version` ist zum Zeitpunkt von
    `SaveAsync` bereits der Ziel-/Endstand NACH den neuen, noch ungespeicherten
    Events — nicht der Stand VOR ihnen.
  - Laut Marten/JasperFx.Events XML-Doku (JasperFx.Events.xml,
    `IEventOperations.Append(string, long, ...)`): "Append events to an existing
    stream and verify that the maximum event id for the stream matches the
    supplied expected version" — d. h. der Parameter muss der Stream-Stand VOR dem
    Append sein (= `basePosition`), nicht der Stand danach.
  - `basePosition` wird im Code korrekt berechnet, aber nur für die Outbox-
    Message-Positionen verwendet — nicht für den `Append`-Aufruf selbst.

Konsequenz (falls die obige Lesart zutrifft): Der optimistic-concurrency-Check
prüft gegen den falschen (zu hohen) erwarteten Stream-Stand, was bei jedem Save
mit mind. einem neuen Event zu einer fälschlich ausgelösten (oder bei
Neuanlage eines Streams: garantiert fehlschlagenden) `ConcurrencyException`
führen dürfte, statt wie dokumentiert nur bei echten Konflikten.

Empfehlung: Verifizieren (z. B. per Integrationstest gegen echtes Postgres/Marten,
siehe auch Punkt [2]) und ggf. `session.Events.Append(streamKey, basePosition,
uncommittedEvents)` verwenden.

Positiv-Abgleich (keine Abweichung, zur Vollständigkeit)
-------------------------------------------------------------------------------------------------
- BuildingBlocks.Application (ISender, ICommand/IQuery(+Handler), IPipelineBehavior,
  Result/Result<T>/Failure/FailureCategory, IRepository, IUnitOfWork,
  IEventSourcedRepository, IProjectionHandler, IDomainEventPublisher,
  IIntegrationEvent(Mapper)) bildet die Doku 1:1 ab, inkl. XML-Doc-Konventionen
  (ADR-0013) und Zero-Dependency-Regel (.csproj hat keine PackageReferences).
- Pipeline-Behavior-Reihenfolge ExceptionToResult -> Logging -> UnitOfWork ->
  Handler ist sowohl in ServiceCollectionExtensions.AddBuildingBlocks (Registrierungs-
  reihenfolge) als auch in Sender.BuildPipeline (Wrapping-Logik) korrekt umgesetzt.
- ExceptionToResultBehavior/UnitOfWorkBehavior übersetzen die dokumentierten
  Exception-Typen (DomainValidationException, BusinessRuleViolationException,
  Marten ConcurrencyException, EF Core DbUpdateConcurrencyException) exakt wie
  in ADR-0017/0019 beschrieben in die passenden FailureCategory-Werte.
  - EfCoreRepository/EfCoreUnitOfWork, MartenEventSourcedRepository/MartenUnitOfWork
  folgen den "kein Update, keine Query-Methoden außer GetByIdAsync, kein Marten-
  Apply-Convention"-Vorgaben aus §3 der Infrastructure-Doku.
- Ordnerstruktur (Dispatching/, Persistence/, Outbox/, Events/, Messaging/,
  DependencyInjection/) entspricht exakt der Capabilities-Tabelle in
  building-blocks-infrastructure.md.
- "Contracts live in the innermost layer that consumes them" (ADR-0024) wird
  eingehalten: IOutboxStore, OutboxMessage, IIntegrationEventTransport bleiben
  Infrastructure-intern, keine Leckage von Infrastruktur-Konzepten nach Application.
